# 🛡️ 线索状态机流转与容灾回滚机制 (State Machine & Rollback Rules)

在分布式异步架构中，为防止网络波动、数据库超时引发的**“脏数据 / 状态卡死 / 外部动作并发重放”**等脑裂问题，本系统的线索处理器（`clue_handler`）全量采用并落地了以下核心安全防线原则：

## 核心设计范式：抢先落库防脑裂

**标准处理编排模型（Transaction-like Workflow）：**
1. **获取锁并抢先占位 (Lock & Pre-Update)**：在发起任何【外部不可逆副作用】（如外呼、微信通知、第三方排期）前，强制通过 `update_clue_state_or_raise` 将本地线索更新为下一步的“安全占位状态（如 `WAIT_FOR_CALLING` / `PENDING`）”。
2. **执行动作 (Perform External Action)**：带超时控制地执行副作用。
3. **失败回滚/拦截阻断 (Rollback & Short-circuit)**：如果步骤2失败，拦截异常并将状态滚回重试池（如 `PENDING`）或直接降级沉入失败终态（`REJECTED`）。

---

## 🔁 各业务模块流转与回滚规则说明

以下是系统中各核心动作的状态跃迁及回退处理规则：

### 1. 接入新线索分发 (`new_clue.py`)
主要负责处理从接入层下发的新鲜线索（`CREATED` 状态），决定是立即外呼还是放进任务池。

* **动作 A：立即呼叫（工作时间）**
  * **先占位**：`CREATED` ➡️ `WAIT_FOR_CALLING`
  * **发动作**：调用百炼大模型外呼系统的拨打能力 `call_voice_agent`。
  * **回滚规则**：若接口超时或响应失败，将其直接回滚并定死终态：`WAIT_FOR_CALLING` ➡️ `REJECTED`，防止无效线索在系统内部积累死锁。

* **动作 B：定时排期入池（非工作时间）**
  * **先占位**：`CREATED` ➡️ `SCHEDULED`
  * **发动作**：调用系统异步定时队列接口 `schedule_repeat_call`。
  * **回滚规则**：若外部定时任务建立失败，回滚状态：`SCHEDULED` ➡️ `REJECTED`。

### 2. 话后状态收口与决策 (`call_end.py`)
外呼结束时触发的回调处理分析器。

* **动作 A：需次呼排期 (`code=500`)**
  * **先占位**：`CALLING` ➡️ `SCHEDULED`
  * **发动作**：下发次日或定时重呼任务。
  * **回滚规则**：如果排期的外部队列服务挂了，直接回滚断停为终态：`SCHEDULED` ➡️ `REJECTED`，并用作 `[300, 323]` 报文向上游上报拦截。

* **动作 B：离线派发加微及监控请求 (`code=600`)**
  * **先占位**：`CALLING` ➡️ `PENDING`（即等待加微结果）。
  * **发动作**：调用 `send_wechat_add_request` 并设置等待闹钟 `schedule_wechat_accept_monitor`。
  * **回滚规则**：只有微信发送与闹钟设定全链路 (`A and B`) 通过才安全驻留 `PENDING`。只要任意外部环路断裂失败，立即清理现场：`PENDING` ➡️ `REJECTED`。

* **动作 C：外呼内顺道加微 (`code=700/900`)**
  * **规则**：类似上述，落库 `PENDING` 失败则阻断，设定超时监控队列失败即回滚至 `REJECTED`。

### 3. 定时重载任务处理器 (`scheduled.py`)
该逻辑由外部定时系统回调发起。

* **动作 A：唤醒次呼 (`SCHEDULED` to Calling)**
  * **先占位**：`SCHEDULED` ➡️ `WAIT_FOR_CALLING`（抢到即剥夺他人调度此线索能力）。
  * **发动作**：调用呼叫接口分配通道与话术。
  * **回滚规则**：呼出发生任何异常请求（网络波动等），将线索踢掉并抛送终态同步给业务系统：`WAIT_FOR_CALLING` ➡️ `REJECTED`。

* **动作 B：监测加微超时 (`PENDING` timeout)**
  * **规则**：到达时间依旧在 `PENDING`，直接将其抛入废弃终态 `REJECTED` 并通知业务测未通。

### 4. 业务强制主动撤单 (`cancel_clue.py`)
发生于人工客服介入或者业务侧认为该线索不再重要时进行拦截。

* **先占位保护**：`CALLING / WAIT_FOR_CALLING` ➡️ `WAIT_FOR_CANCEL`
* **发动作**：命令外呼中心撤下其拨号或电话挂断指令：`cancel_call()`。
* **分流抉择**：
  * **成功撤下**：安全跃签 `WAIT_FOR_CANCEL` ➡️ `REJECTED` 结单。
  * **撤下失败 / 被外呼系统拒绝响应**：不再强制转跳终态，保持在安全隔离带 `WAIT_FOR_CANCEL` 不变，由外呼平台随后正常的最终流转回调自动将其带走（防止人工强锁失败与流转系统顶牛死磕）。

### 5. 通道侧离线微信状态回调 (`channel.py`)
用于最终拦截到【用户通过了微信好友】及结束成功信息反馈给平台。

* **通过时 (Accept)**：
  * **防并发封堵**：检查状态当前不是 `ACCEPTED`，抢先调用抛错版本强锁落库 ➡️ `ACCEPTED`。
  * **终态确认**：向主业务系统发出业务通知 `finalize_clue`。
  * **补偿回滚 (DLQ核心机制)**：业务侧返回失败了怎么办？此时必须记录异常并将状态强行从已关闭再次向后**回退重展**：`ACCEPTED` ➡️ `PENDING` 并抛出错误阻断协程！外侧 Redis 被抛出错误打退后，过一阵子会自动再次取出线索消费，从而完美实现了对业务系统失败断服时的“最终一致性重试补偿”。

* **拒绝/加微被忽略超时 (Reject)**：
  * **封堵落库**：抢先打入 `REJECTED`。
  * **补偿回滚**：通知外系统失败同样逆反状态回退到 `PENDING` 然后中断，抛给主消息系统的兜底补偿。

## 🔒 异常拦截机制底层依赖
依赖于底层的 `app.dbmodels.crud.update_clue_state_or_raise` 函数。
所有的抢先占位或者是后续回滚，只要：
1. **触发流转规范中不在 `VALID_TRANSITIONS` 支持列表的操作。**
2. **多并发下 SQLite 获取锁抢用超时 (`16s` 等不到系统资源释放)。**

都会被底层瞬间原抛 `Exception`，进而中断该阶段的所有操作，保障了内存无死锁并且动作不漏发错发，由最外层的控制总程将其退回原点或报警。
